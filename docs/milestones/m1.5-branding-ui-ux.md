## Approved direction

Nico selected **option B — restrained iris accent** after comparing it with the
monochrome treatment on the same Checkout screen.

- Keep the black/white/gray foundation and quiet workspace chrome.
- Use iris sparingly for selection, active controls, and related connections.
  Neutral nodes and surfaces keep the graph readable and visually dominant.
- Carry forward the comparison's compact controls, fine borders, restrained
  node styling, contextual inspector, and command-palette direction.
- Treat the prototype as the visual baseline. It demonstrates selection,
  label editing, undo/redo, and commands; full canvas behavior remains work for
  the actual editor.
- Light-theme accent tokens: `#565ac2` for focus/selection, `#f0f0fa` for soft
  surfaces, and `#777bd1` for accent borders. Dark-theme prototype values are
  not part of this implementation.
- Typography is Geist Sans + Geist Mono, with a regular-weight lowercase
  wordmark. Primary buttons are graphite, leaving iris for orientation and
  selection. Nico's mark appears in the header and as a static SVG favicon.

## Design direction

- **References: Linear, Raycast, and Resend.** Use them as references for restraint,
  precision, and a premium developer-tool feel. Establish Statecraft's own
  identity around flows and their connections to code.
  Resend reinforces attention to small details, speed, and predictable developer
  experiences; see its [design philosophy](https://resend.com/philosophy) and
  [brand kit](https://resend.com/brand).
- **Canvas first.** Nodes, connections, and the current selection carry the
  hierarchy. Keep navigation, toolbars, and the inspector visually quiet and
  compact enough to leave meaningful working space.
- **Neutral foundation with iris.** Use black, white, and nuanced grays with the
  approved restrained iris accent. It should help orientation while preserving
  the canvas hierarchy. Validate semantic tokens and usage rules in the editor.
- **Meaningful color.** Separate brand, selection/focus, and semantic feedback.
  Distinguish node kinds and connection outcomes with labels, shapes, or icons
  as well as any color. Preserve graph readability in a monochrome view.
- **Precision in the details.** Consistent spacing, optical alignment, typography,
  icon weight, borders, radii, focus rings, hit areas, and microcopy. Design hover,
  pressed, focused, selected, disabled, empty, and error states together.
- **Direct interaction.** Familiar frontend-engineer conventions, discoverable
  shortcuts, predictable focus, and immediate feedback. The interface should
  remain comfortable during repeated use.
- **Purposeful motion.** Small, interruptible transitions explain a change or
  connect related states. Pan, zoom, dragging, and selection must feel immediate.
  Avoid ambient effects that distract from the flow.

## Work packages, in order

### 1. Finalize the approved visual direction

- Completed: compare monochrome and restrained iris on the same Checkout canvas,
  toolbar, and inspector, keeping layout, content, typography, and theme identical.
  Nico approved the iris treatment on 2026-09-24; use it as the visual baseline.
- Choose typography, icon language, density, and a small Statecraft wordmark or
  mark usable in the app and as a favicon.
- Completed: M1.5 ships light mode; dark mode is a separate design step.
- Record the chosen direction and its rationale before applying it everywhere.

### 2. Build the visual foundations and workspace shell

- Define semantic tokens for surfaces, text, borders, interaction states,
  semantic feedback, spacing, typography, radii, shadows, and motion.
- Apply reusable controls to flow naming, file actions, history, the node palette,
  and the inspector. Clarify primary, secondary, and destructive actions.
- Give the canvas room at common laptop sizes. Ensure constrained widths and
  browser zoom do not make essential controls inaccessible.
- Preserve clear feedback for unsaved changes, local saves, imports, and storage
  errors without making the header visually busy.

### 3. Refine the canvas and inspector

- Give the five node kinds a coherent visual language: Screen, UI, Action,
  Service, and State. Resolve long labels and entry-point treatment.
- Refine handles, edges, edge labels, selection, keyboard focus, and multi-select
  treatment so their states remain distinct and legible at useful zoom levels.
- Make connection affordances, valid/invalid targets, and selected elements clear.
- Design the empty canvas, no-selection inspector, single selection, multiple
  selection, inline editing, and destructive-action feedback as one experience.
- Keep inspector changes stable: predictable focus and layout, no distracting
  jumps as selection changes.

### 4. Make keyboard and pointer workflows coherent

Define one command registry for existing editor actions and use it for visible
controls, shortcut hints, and a small command palette. Code-entity search stays
in M3. The following bindings are a starting proposal to validate in-browser:

| Action | Proposed convention | Scope |
| --- | --- | --- |
| Undo / redo | Cmd/Ctrl+Z; Cmd/Ctrl+Shift+Z | Editor history outside text editing; retain native text undo inside fields |
| Save locally | Cmd/Ctrl+S | Active workspace, with visible success/error feedback |
| Command palette | Cmd/Ctrl+K | Active workspace; restore focus on close |
| Delete selection | Backspace / Delete | Focused canvas, outside editable fields; one undoable operation |
| Select all | Cmd/Ctrl+A | Focused canvas; native text selection in fields |
| Cancel / dismiss | Escape | Close the innermost transient UI or cancel an edit first |
| Navigate controls | Tab / Shift+Tab, Enter / Space | Logical focus order and standard control behavior |

- Show platform-appropriate shortcut labels. Verify browser conflicts and
  AZERTY/QWERTY behavior before finalizing the map.
- Define pan/zoom, selection-box, additive-selection, and fit-view behavior for
  mouse and trackpad. Expose important actions in visible controls too.
- Keep text inputs, contenteditable elements, IME composition, and dialogs safe
  from unrelated global shortcuts. Preserve browser/OS shortcuts outside the
  relevant editor context.
- Provide a keyboard path for adding, selecting, editing, and deleting flow
  elements. Connections remain a direct pointer interaction, as agreed with
  Nico; drag and drop is not the only way to add nodes.
- Include accessible names, clear focus indicators, focus restoration, concise
  tooltips with shortcut hints, and a discoverable shortcut reference.

### 5. Add motion and interaction finishing

- Define shared motion tokens after trying them in the actual editor. Initial
  exploration ranges: 100–160 ms for small feedback and 160–220 ms for transient
  panels or menus; these are proposals, not a previously chosen motion system.
- Keep direct manipulation attached to the pointer. Do not add tweening that
  makes nodes trail dragging or delays selection feedback.
- Handle interruption and repeated actions without queues, flashes, or snapping.
- Respect reduced-motion preferences; feedback must remain understandable when
  movement is removed. Avoid perpetual animation and ornamental edge motion.
- Check tooltip delays, menu positioning, hover-to-focus continuity, truncation,
  loading/disabled states, and reversible deletion.

### 6. Verify the experience and prepare a demonstration

- Capture a baseline before visual/motion changes, then profile the same actions
  on Checkout and a denser fixture of roughly 100 nodes with a recorded edge
  count. Record the machine, browser, and fixture for meaningful comparisons.
- Check pan, zoom, node dragging, multi-selection, inspector edits, and undo/redo
  for rendering regressions. Target smooth interaction at the display's refresh
  rate and investigate main-thread stalls instead of relying only on appearance.
- Validate keyboard workflows, focus, text editing, contrast, reduced motion,
  long labels, empty states, import failures, and local-storage failures.
- Run the repository checks and targeted behavior tests for new commands or
  focus-sensitive interactions. Visually inspect the complete editing journey.
- Prepare a repeatable Checkout journey: add, connect, select, edit, undo/redo,
  save, and reopen. Capture before/after images and a short recording when
  preparing build-in-public material; media production is a separate task.

## Completion criteria

- A chosen visual direction, theme scope, and token system are documented and
  consistently applied to the existing canvas workspace.
- The Checkout editing journey works through pointer and keyboard workflows;
  commands respect focus, text editing, undo history, and platform conventions.
- Nodes and edges remain the visual priority; selection, focus, node kinds, and
  connection outcomes are distinguishable without relying only on color.
- Motion is coherent, interruptible, and compatible with reduced motion, with
  no unresolved interaction regressions in the recorded profiling scenarios.
- Empty, error, disabled, and persistence states receive the same level of care
  as the normal editing state.
- The Checkout fixture and verified journey are ready to support a
  build-in-public recording. Producing and publishing media are separate tasks.

## Final UI verification — 2026-10-08

Checked the production Vite build in Codex in-app Chromium on macOS, with
Checkout and an isolated local preview origin for storage failures. The checkout
path had previously covered adding and naming a node, connecting it, changing
the edge kind, undo/redo, saving, reloading, exporting and reopening JSON.

- At 375 px and 800 px, the workspace and header controls remained accessible
  without document-level horizontal overflow. Fit View, the inspector, and the
  empty-state and persistence controls were available. The graph needs pan/zoom
  at narrow widths; it is not intended to fit legibly in a phone-sized canvas.
- A long service label wrapped within its node, updated adjacent accessible edge
  labels, and did not create document-level horizontal overflow.
- An invalid JSON import kept the current flow and showed a readable,
  actionable toast at 375 px. Clicking the message dismissed it.
- An invalid saved draft showed a warning with Export and Replace actions. When
  local storage was unavailable, the warning offered Export and Save. A failed
  save changed the main action to Retry save and offered Export in its toast;
  the toast stayed within a 375 px viewport.
- Keyboard navigation reached an edge with its accessible label. The canvas,
  nodes, edges, controls, inputs and buttons define visible focus treatments.
- Computed light-theme contrast against white: foreground 16.03:1, muted text
  5.67:1, iris text/focus 5.77:1, danger text 6.47:1. Accent borders measured
  3.79:1. These are targeted token checks, not a complete accessibility audit.
- The logo animation is guarded by `prefers-reduced-motion: no-preference` in
  CSS. Nico subsequently verified the reduced-motion setting and browser zoom
  on 2026-10-08; both behaved as intended.
- `pnpm build` and `pnpm test` passed (106 tests). Web lint passed with the
  existing React refs warning in `App.tsx:132`. Vite still reports the existing
  bundle-size warning. No UI defects requiring code changes were found in these
  checked states.
